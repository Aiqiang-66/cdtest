# Phase 1：输入注入 + 历史资料召回 + 需求分析 + 用例生成 — AI 驱动版

## 定位

**固定骨架 + AI 填充**模式：AI 在固定流程骨架内自主收集输入、匹配历史资料、分析需求、生成用例。具体输入来源和用例生成规则由 AI 根据上下文动态判断。

## Phase 1.0：Confluence 知识搜索（新增前置步骤）

### 触发条件

```yaml
# 每次执行 Phase 1 需求分析前，必须先执行 Confluence 知识搜索
# 仅在以下情况可跳过：
#   - 用户明确要求不搜索历史资料
#   - MCP（星河文档 server）不可用（getConfluenceStatus 检查失败）
```

### 搜索流程

```yaml
1. 检查 MCP 可用性:
   - 调用 mcporter call 星河文档 getConfluenceStatus
   - 如果不可用 → 跳过知识搜索，记录"Confluence 知识库不可用"到测试报告
   - 如果可用 → 继续执行

# ⚠️ 硬限制（防止无限搜索）:
#   - Phase 1.0 中 searchConfluenceKnowledge 最多调用 4 次
#   - searchConfluenceTracking 最多调用 2 次
#   - 达到上限后即使结果不足也不追加搜索，使用已返回的结果
#   - limit 参数单个搜索建议 30-50，最大不超过 100

2. 识别业务线:
   - 从需求文本中提取业务线关键词
   - 如果是中台项目（ADS投放中台/OA/ERP/权限等），业务线为"中台"，目录ID=87270532
   - 如果是C端用户项目（书城/签到/阅读等），业务线为"阅读"，目录ID=2720054
   - 如果是短剧类项目，业务线为"短剧"，目录ID=33292986
   - 如果是圣经类项目，业务线为"圣经"，目录ID=124675362
   - 如果是分销类项目，业务线为"分销"，目录ID=92741821
   - 如果是KOC类项目，业务线为"KOC"，目录ID=161749067
   
   ⚠️ 如果不确定产品线，必须先询问用户确认，不能自行假定
   ⚠️ 跨业务项目（如中台影响C端）需要搜索多条业务线的历史资料

3. 确定搜索内容:
   - 从需求文本中提取关键搜索词：
     * 功能名称：如"ROI统计"、"报表"、"筛选器"
     * 模块名称：如"国剧"、"海剧"、"广告"
     * 技术关键词：如"TiDB"、"StarRocks"、"数据源"
     * 业务关键词：如"短剧"、"推广"
   
   - AI 自行补充搜索词范围：
     * 近义词：报表→统计/报告/看板
     * 关联功能：查询→筛选/过滤/搜索
     * 历史功能名：从需求中的URL/菜单路径提取

   - 时间范围：不限制搜索时间范围（搜索全量历史资料）

4. 执行知识搜索（searchConfluenceKnowledge）:
   mcporter call 星河文档 searchConfluenceKnowledge queryText="{搜索词}" directories="[{目录ID}]" limit={结果数}
   
   - 搜索词：组合关键词，如"国剧 ROI 报表 筛选器"
   - 目录ID：从业务线对照表获取，多个业务线用逗号分隔 "[87270532,33292986]"
   - 结果数：初始搜索50条，如不足再扩大至100条

5. 搜索埋点相关（searchConfluenceTracking）:
   - 触发条件：需求涉及以下内容时必须搜索：
     * 数据指标：ROI/CPM/CTR/CVR/消耗/流水/转化
     * 报表/统计：任何数据展示类功能
     * 埋点：用户行为/事件统计
     * 广告相关：收入/支出/归因
   
   mcporter call 星河文档 searchConfluenceTracking queryText="{搜索词}" directories="[{目录ID}]" limit={结果数}
   
   - 搜索词：如"国剧 ROI 字段 口径"、"广告 归因 数据"
   - 目录ID：同业务线对照表
   - 结果数：初始搜索50条，如不足再扩大至100条

6. 处理搜索结果:
   - 阅读搜索返回的 relevantContext 中的 text 和 title
   - 打开感兴趣的结果 webUrl 进一步查看（如需）
   - 提取以下信息：
     * 历史功能点：哪些是已有逻辑
     * 历史风险点：之前测试发现的问题
     * 字段口径：指标计算公式/数据来源
     * 菜单路径：页面如何组织
     * 兼容约束：历史数据/命名规范等限制
   
   - 搜索结果结构化输出到测试方案中：
     * "历史资料检索结果"章节
     * 列出：文档标题、URL、匹配内容、对本需求的参考价值
```

### 搜索策略示例

```yaml
# 场景：国剧ROI报表测试
需求内容: "视频国剧ROI报表（video-cn-report-roi），TiDB数据源"
业务线: "中台"（ADS投放中台），目录ID=87270532

### 搜索结果的应用

```yaml
# 搜索到的历史资料必须应用到以下环节：
1. 测试方案（Phase 1.2）:
   - 在"历史已有逻辑 vs 本期新增逻辑"中引用
   - 标注来源文档的 webUrl

2. 用例生成（Phase 1.3）:
   - 从历史需求中提取 P0/P1 回归用例

   - 标注回归用例的来源（"来自历史需求 X"）

3. 交互探索（Phase 3a）:
   - 根据历史菜单路径预判页面结构
   - 注意历史字段口径与当前页面展示的一致性

## Phase 1.0.5：MCP 测试用例知识库查询（新增步骤）

### 触发条件

```yaml
# Phase 1.0（Confluence 知识搜索）完成后执行
# 查询 MCP 测试用例知识库中的历史用例，供 Phase 1.3 用例生成时参考
触发:
  - MCP Test Case Server 可用（getTestCaseStatus 返回 configured: true）
  - requirement_meta.json 中 system 已确定（Phase 0 产出）

跳过:
  - MCP 不可用 → 仅使用 Confluence 搜索结果 + 通用知识库
  - system 未确定 → 提示用户补充后继续
  - 用户明确要求不查询历史用例
```

### 搜索流程

```yaml
1. 检查 MCP 可用性:
   mcporter call test-case-mcp getTestCaseStatus
   - configured=false → 跳过，记录"用例知识库未配置"

2. 基础搜索（按系统+业务类型）:
   mcporter call test-case-mcp searchTestCases \
     system="<requirement_meta.system>" \
     businessType="<requirement_meta.businessType>" \
     limit=50

3. 语义搜索（按需求关键词）:
   # 从需求文本提取 3-5 个核心关键词
   mcporter call test-case-mcp searchTestCases \
     system="<requirement_meta.system>" \
     businessType="<requirement_meta.businessType>" \
     caseNameSemanticQuery="<关键词组合>" \
     caseNameSemanticMinScore=0.5 \
     limit=30

4. 版本过滤（可选）:
   # 如果 Confluence 搜索结果中提到历史版本号，可直接查该版本
   mcporter call test-case-mcp searchTestCases \
     system="<requirement_meta.system>" \
     requirementVersion="<历史版本号>" \
     limit=50

⚠️ 硬限制（防止过度搜索）:
  - Phase 1.0.5 中 searchTestCases 最多调用 3 次
  - 达到上限后使用已有结果，不追加搜索
```

## Phase 1.1：输入注入与历史资料召回

### AI 判断框架

```yaml
# AI 在收到输入时自动执行以下流程：
1. 收集输入:
   - AI 自动扫描可用输入源：
     - spec/ 目录下的文档（PRD/开发文档/测试文档）
     - 用户直接描述的需求
     - 用户提供的截图/链接
   - AI 判断：哪些输入与当前测试相关？哪些可以忽略？

2. 识别业务模块:
   - AI 从需求文本中提取关键词
   - AI 判断：这个需求属于哪个业务模块？
   - AI 不预设模块列表，每次根据上下文动态判断
   - ⚠️ 如果不确定 → 询问用户确认（参见 Phase 1.0 §2）

3. Confluence 知识搜索:
   - 按照 Phase 1.0 流程执行搜索
   - 从搜索结果中提取历史逻辑、风险点、字段口径

4. 匹配历史资料:
   - AI 读取 references/historical-case-index.md
   - AI 判断：当前需求与哪些历史模块相关？
   - 命中 → AI 继承该模块的风险点和回归用例参考
   - 未命中 → AI 标注"历史资料未命中"，基于通用经验推断

5. 提取配置:
   - AI 从 spec/ 文档和 Confluence 搜索结果中自动提取：
     - 测试 URL / APP 包名
     - 登录凭证
     - DB 连接信息
     - API Base URL
     - 设备 ID
   - AI 判断：哪些配置是必需的？哪些是可选的？
```

## Phase 1.2：产品需求解读与影响分析

### AI 判断框架

```yaml
# AI 在解读需求时自动分析以下维度：
1. 业务目标:
   - AI 理解：为什么要做这个需求？
   - 示例：提升广告收入 / 优化用户体验 / 增加转化率

2. 用户路径:
   - AI 推导：用户从哪里进入？做什么？结果是什么？
   - 示例：书城 → 搜索 → 详情页 → 加入书架 → 阅读

3. 变化分析:
   - AI 区分：历史已有逻辑 vs 本期新增逻辑 vs 本期修改逻辑 vs 保持不变逻辑
   - ⚠️ 必须结合 Confluence 搜索结果来判断哪些是"历史已有逻辑"
   - AI 判断：哪些变化会影响哪些模块？

4. 影响范围:
   - AI 分析：这个需求会影响哪些页面/接口/配置/数据/商业化链路？
   - AI 不预设影响范围表，每次根据上下文动态判断
   - ⚠️ 跨业务线影响检查：当前需求是否影响其他业务线？
     - 例如：中台的报表需求是否影响短剧/国剧的数据展示？
     - 如果是 → 需要跨业务线搜索历史资料

5. 风险分析:
   - AI 从 Confluence 搜索结果和历史风险点中提取风险项
   - 新增风险（基于本次需求的新功能）
   - 历史重现风险（之前出过问题的地方）
   - ⚠️ 每个风险必须标注来源（Confluence 文档 / 历史用例 / 代码审查）

6. 待确认问题:
   - AI 识别：需求中哪些地方没写清楚？
   - AI 列出：需要确认的问题列表

7. 跨平台依赖（混合模式）:
   - AI 判断：这个需求是否需要 Web 后台配合？
   - 是 → AI 标记为混合模式，拆分 Web/APP 职责

8. 搜索补充（可选）:
   - 如果 Phase 1.0 的搜索结果不足以覆盖所有维度
   - AI 可发起第二轮搜索，使用新的关键词
   - 场景：发现需求涉及未搜索过的子模块时
```

## Phase 1.3：用例生成

### AI 判断框架

```yaml
# AI 在生成用例时自动执行以下流程：
1. 选择模板:
   - AI 根据平台选择对应模板：
     - Web → 12 字段模板（引用 case-template.md）
     - APP → 21 字段模板（引用 case-template.md）
   - AI 确保字段值符合值域约束

2. 设计测试类型:
   - AI 为每个功能点设计用例，引用 `common/execution-optimization.md §七 深度测试矩阵`:
     功能类型   | 正常流 | 边界值 | 组合场景 | 异常流 | 数据验证
     ----------|--------|--------|----------|--------|---------
     筛选条件   |   +    |   +    |    +     |   +    |   —
     排序       |   +    |   —    |    +     |   —    |   +
     报表表格   |   +    |   —    |    —     |   +    |   +
     导出       |   +    |   —    |    —     |   +    |   ○
     搜索       |   +    |   +    |    —     |   +    |   —
     表单输入   |   +    |   +    |    ○     |   +    |   —
     配置修改   |   +    |   —    |    ○     |   +    |   —
     数据源切换 |   +    |   —    |    +     |   —    |   —
   
   - AI 根据功能点类型查矩阵，+ = 必须生成用例，○ = 可选，— = 不需
   - 不预设测试类型表，每次根据功能特点动态设计

3. 确定优先级:
   - AI 根据以下因素动态确定优先级：
     - 功能重要性（核心链路 vs 次要功能）
     - 影响范围（影响多个模块 vs 仅影响单个模块）
     - 风险等级（涉及商业化/支付 → 高优先级）
     - ⚠️ 来自 Confluence 搜索的历史风险点 → 提升优先级
     - ⚠️ 从历史需求中提取的回归用例 → 至少 P1
   - AI 不预设优先级表，每次根据上下文动态判断

4. 生成回归用例:
   - AI 根据历史资料匹配结果生成回归用例：
     - 自动触发: 以下信号出现时强制生成回归用例:
       * Confluence 搜索命中 ≥ 1 条相关文档 → 逐条检查是否与当前功能点相关
       * historical-case-index.md 命中模块 → 继承该模块的"示例风险点"
       * 需求文本含 "修改/优化/升级/重构/调整" → 被修改功能原有正常流用例需回归
     - 回归用例分类:
       * RG-DIRECT: 涉及被修改功能的直接回归（原有用例重跑）
       * RG-INDIRECT: 受影响模块的间接回归（需分析影响范围后生成）
       * RG-HISTORY: 历史风险点专项回归（来自 Confluence/历史模块表）
     - ⚠️ 必须引用 Confluence 搜索到的历史需求
     - AI 确保每条回归用例有来源（来自哪个 Confluence 文档 ID / 历史模块）
     - 回归用例 ID 格式: TC-{模块缩写}-RG-{序号}

	4.5. 整合 MCP 历史用例知识库:
	   - 从 Phase 1.0.5 的 historical_cases.json 中提取相关历史用例
	   - 整合优先级（当前需求为主，历史用例为辅）:
	     a) 当前需求明确指定的功能 → 按需求描述生成用例，作为权威来源
	     b) 历史用例中与当前功能点匹配的 → 补充边界/异常/回归场景
	     c) 历史用例的验证点写法（具体检查项）→ 参考复用
	   - 处理规则:
	     - 历史用例的 testSteps 不直接复制，需根据当前页面结构适配
	     - 历史用例的 expectedResult 不直接复制，需对比当前需求是否能匹配
	     - 历史用例的场景在当前需求中被删除/重构 → 不纳入，标注“已废弃”
	   - ⚠️ 每条补充的历史用例必须标注来源: “来自历史用例 {id} (v{requirementVersion})”

	4.6. 冲突检测（对比当前需求 vs 历史用例）:
	   - 对每个当前需求用例，在历史用例中查找同 module + 同功能点的用例
	   - 对比 testSteps / expectedResult / verificationPoint，发现差异后判断类型:
	     * 正常演进: 新增字段/新增步骤/新增验证 → 不冲突，正常合并
	     * 逻辑冲突: 相同字段不同定义/相同步骤不同顺序/相同操作不同预期 → 记录
	   - 冲突类型:
	     * A.字段口径: 同一数据字段定义不同（如 ROI=消耗/展示 vs ROI=收入/成本）
	     * B.流程步骤: 同一操作步骤顺序不同（如先审核后提交 vs 先提交后审核）
	     * C.预期结果: 同一操作结果矛盾（如删除后列表刷新 vs 删除后跳转回收站）
	   - 输出 conflicts.md:
	     | # | 类型 | 当前需求 | 历史用例(来源) | 冲突描述 | 影响范围 | 建议 |
	   - 冲突用例标记为“待确认”，不阻塞其他用例执行
	   - ⚠️ 必须提示用户确认: “发现 N 个逻辑冲突，请逐条确认采用哪个版本”
	   - 用户确认前不对冲突用例做删除/覆盖

5. 引用测试知识库补充验证点（分类触发，非逐条遍历）:
   - ⚠️ 先判断功能类型，仅引用相关章节（避免对所有功能做全量逐项检查）:
     
     功能类型 → 应检查的知识库章节:
       纯查询/展示页面（无输入） → §二 查询操作 + §九 错误页面
       表单输入页面              → §一 输入框 + §二 增删改 + §九 错误页面
       报表/统计类页面           → §二 查询操作 + §四 性能 + §九 错误页面
       配置修改页面              → §二 修改操作 + §九 错误页面
       登录页面                  → §八 登录模块
       APP 测试                  → 以上相关章节 + §五 APP专项
     
     检查方式:
       - 为功能页面匹配到章节后，仅扫描该章节的验证点
       - 对每个验证点: 判断是否适用于当前功能 → 适用则生成对应用例 → 不适用则标注跳过原因
       - 不再要求对所有 §1-§9 做全量遍历

6. 自我审查（验证完整性和遗漏）:
   - AI 生成用例后自动审查：
     - 是否有遗漏的测试类型？（正常流/边界值/异常流）
     - 是否有遗漏的页面元素？
     - 是否有重复用例？
     - 优先级是否合理？
     - ⚠️ 是否有遗漏 Confluence 搜索结果中的关键逻辑？
     - ⚠️ 是否有遗漏测试知识库中的通用验证点？
       * 输入框验证：长度/边界/特殊字符/唯一性 是否都已覆盖
       * 功能操作验证：增删改查的提示/限制/重复提交 是否都已覆盖
       * 界面临界场景：快捷键/Tab键/多分辨率/错误友好性 是否都已考虑
   - 审查不通过 → AI 自动补充/调整

7. 用例排序（生成完成后执行）:
   - AI 按以下规则排序用例执行顺序：
     - 第一关键字: 优先级（P0 → P1 → P2 → P3）
     - 第二关键字: 依赖关系
       * 在用例 `dependency` 字段中标记依赖用例 ID
       * 例如: TC-PL-002 依赖 TC-PL-001 → TC-PL-001 必须在前
       * 产生数据的用例先于消费数据的用例
       * 循环依赖检测: 如发现 A→B→A → 提示用户确认优先级
     - 第三关键字: 页面聚合（同一页面的用例相邻执行，减少页面跳转）
     - 第四关键字: 操作类型（浏览/验证类先于修改/删除类）
   - ⚠️ 排序后不重新编号: ID 在生成时已确定，排序只调整执行顺序字段（order/seq），
     不改变 case_id，确保 dependency 引用始终有效

## Phase 1.4：探索反馈 → 用例补充（执行模式专属）

### 触发时机

```yaml
# Phase 1.4 在 Phase 3a（交互探索）完成后触发：
触发条件:
  - exploration_result.json 中 discovery_gaps 数组非空
  - 即：探索发现存在未覆盖的页面或未覆盖的操作

不触发条件:
  - discovery_gaps 为空 → 跳过 Phase 1.4，直接进入 Phase 3b
  - 设计模式 → 跳过 Phase 1.4（无探索阶段）

备选触发（即使 discovery_gaps 为空也检查，带具体执行指令）:
  场景 1 — 初始用例总数 < 5 条:
    → AI 必须依次检查是否遗漏:
      a. 页面加载/可达性验证用例
      b. 每个可见 CRUD 按钮（新增/编辑/删除/搜索/导出）的点击验证用例
      c. 空数据/边界值 至少各 1 条
    → 如遗漏 → 生成补充用例（标记 source="备选触发-用例不足"）

  场景 2 — 所有用例的测试类型都是"功能"（无 边界值/异常流程）:
    → 对每个功能点，检查对应知识库:
      - 有输入框？→ 补充 §1 边界值+异常值用例
      - 有提交操作？→ 补充 §4 重复提交/错误处理用例
      - 有查询？→ 补充空数据/无结果用例
    → 如遗漏 → 生成补充用例（标记 source="备选触发-类型缺失"）

  场景 3 — Phase 3a 探索被跳过（但用户未明确要求跳过）:
    → 提示用户: "交互探索阶段被跳过，以下场景可能未被覆盖：新增/编辑弹窗、未在spec中提及的关联页面。是否确认继续？"
    → 用户确认 → 继续 | 用户要求补充 → 执行 Phase 3a
```

### AI 判断框架

```yaml
# 补充范围和优先级判断 → 见 common/discovery-feedback.md（唯一权威来源）
