# 人工依赖 DB 绕过 — AI 驱动版

## 定位

AI 自主判断哪些步骤可以绕过、如何绕过、绕过后的风险。**不预设 12 种场景**，AI 根据上下文动态决策。

## AI 判断框架

```yaml
# AI 在遇到阻塞步骤时自动评估：
1. 识别阻塞:
   - 当前步骤无法通过 UI/API 完成
   - 原因：需要人工操作 / 依赖外部系统 / 等待定时任务
   - AI 判断："这个步骤的本质是什么？"

2. 判断是否可绕过:
   - 可绕过条件：
     - 阻塞步骤的本质是"状态变更"（审批通过/回调触发/定时任务完成）
     - 绕过后的后续步骤有验证价值（至少 2 个可验证步骤）
   - 不可绕过条件：
     - 阻塞步骤的本质是"数据生成"（需要人工输入内容）
     - 绕过后的后续步骤无验证价值

3. 推导绕过方式:
   - 状态变更类 → UPDATE 目标表的状态字段
   - 数据缺失类 → INSERT 必要数据
   - 回调未触发类 → UPDATE 回调状态字段
   - AI 通过 DESC 探查表结构，找到正确的字段名

4. 执行绕过:
   - ⚠️ 必须先记录 before 状态:
     SELECT * FROM {table} WHERE {condition} → 保存完整 before 快照
   - 执行 UPDATE/INSERT
   - 验证影响行数（应为 1 或有限行）
   - 记录 after 状态
   - ⚠️ 如果影响了意外数量的行（如 > 10 行）→ 立即生成逆向 SQL 回滚
     ROLLBACK_SQL: "UPDATE {table} SET {field}={before_val} WHERE {pk}={id}"

5. 标记与清理:
   - 所有绕过操作产生的数据标记 【测试绕过】
   - 记录到报告
   - 测试完成后 AI 自动清理
```

## AI 绕过示例

```yaml
场景: "OA 审批通过" 阻塞
AI 推理:
  - 本质: 状态变更（从"待审批"变为"已审批"）
  - 目标表: 通过关键词"审批/approve"定位
  - 目标字段: 通过 DESC 找到 status/approve_status 字段
  - 绕过: UPDATE {table} SET status='approved' WHERE id=X
  - 风险: 低（状态变更可逆）
  - 后续价值: 可验证审批通过后的 3 个步骤

场景: "支付回调未触发" 阻塞
AI 推理:
  - 本质: 外部系统状态同步
  - 目标表: 通过关键词"支付/payment/order"定位
  - 目标字段: 通过 DESC 找到 payment_status/callback_status 字段
  - 绕过: UPDATE {table} SET payment_status='paid' WHERE id=X
  - 风险: 中（支付状态变更影响后续流程）
  - 后续价值: 可验证支付完成后的 4 个步骤
```

## AI 清理策略

```yaml
# AI 在测试完成后自动执行：
清理策略:
  - 查询所有标记 【测试绕过】 的数据
  - 按创建时间倒序清理（后创建的先清理）
  - 清理前输出清理清单供确认
  - 清理后验证数据已恢复
```
