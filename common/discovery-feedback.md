# 探索发现反馈与用例补充机制

## 定位

**在探索阶段发现与需求相关的弹窗、模态框、功能和链接时，AI 自主判断是否需要补充新用例。**

---

## 核心原则

**不是发现新页面/菜单就无脑补充。只补充与当前需求相关的功能。** AI 必须判断：探索发现的内容是否属于需求触达的业务范围？无关的一律跳过。

---

## 一、核心问题

```yaml
当前问题:
  - 探索阶段发现了新菜单/新页面 → 只记录到 exploration_result.json
  - exploration_result.json 没有被 Phase 1 消费 → 用例集不会自动补充
  - 结果：探索知道有遗漏，但用例集仍是旧的

典型场景:
  1. 需求只提"列表页" → Phase 1 只生成列表页用例
  2. 探索发现列表页有"新增"、"编辑"、"批量导入"等按钮 → 打开弹窗/新页面
  3. 这些弹窗中的表单字段、校验规则 → 完全没有用例覆盖
  4. 此外，列表页可能链接到"详情页"、"配置页"等 → 同样没有用例
  5. 结果：新增、编辑、详情页等场景全部缺失
```

---

## 二、解决方案：探索 → 用例补充闭环

```yaml
闭环流程:
  Phase 1: 生成初始用例集（基于需求/spec）
    ↓
  Phase 2: 造数
    ↓
  Phase 3a: 交互探索（探索页面上的所有交互元素）
    ↓ 输出 exploration_result.json（含 discovery_gaps）
  Phase 1.4: 用例补充 ← AI 消费 exploration_result.json，判断相关性后补充
    ↓ 输出 supplementary_test_cases.json
  Phase 3b: 执行循环（使用完整用例集 = 初始 + 补充）
    ↓
  Phase 3.5: API 测试
    ↓
  Phase 4: 报告
```

---

## 三、相关性判断：补充什么，不补充什么

```yaml
相关性判断是 PHASE 1.4 的核心决策点。

补充的（与需求相关）:
  弹窗/模态框:
    - 需求目标页面上的"新增"弹窗 → ✅ 补充 新增-正常创建 + 新增-必填校验
    - 需求目标页面上的"编辑"弹窗 → ✅ 补充 编辑-正常修改 + 编辑-数据回填 + 编辑-字段校验
    - 需求目标页面上的"删除"确认弹窗 → ✅ 补充 删除-确认删除 + 删除-取消删除
    - 需求目标页面上的"详情"弹窗/抽屉 → ✅ 补充 详情展示验证

  相关功能:
    - 与需求业务链路关联的操作（如"结算"页面的"导出"、"批量导入"） → ✅ 补充
    - 需求功能的状态流转（如提交→审核→完成，用例只覆盖了提交）→ ✅ 补充后续状态
    - 与需求功能有数据关联的配置项 → ✅ 补充配置变更验证

  相关链接:
    - 需求页面内链接到同模块子页面（如"列表页"→"详情页"） → ✅ 补充
    - 需求页面内链接到关联业务模块（如"订单页"→"结算记录"）→ ✅ 补充

不补充的（与需求无关）:
  无关菜单/页面:
    - 帮助页面、关于页面、隐私政策、用户协议 → ❌ 跳过
    - 与需求功能无数据关联的独立模块 → ❌ 跳过
    - 纯展示性落地页（无交互功能） → ❌ 跳过 或 标注"无交互元素"

  无关弹窗:
    - 系统级提示（浏览器版本提示、Cookie 提示）→ ❌ 关闭后跳过
    - 营销弹窗（活动广告、优惠券）→ ❌ 关闭后跳过
    - 无功能的装饰性弹窗 → ❌ 跳过

  无功能元素:
    - 纯装饰性图标/图片 → ❌ 跳过
    - disabled/display:none 的元素 → ❌ 跳过
    - 已废弃功能入口 → ❌ 标注后跳过

  已覆盖的功能:
    - 探索发现与已有用例完全对应 → ❌ 跳过（去重）
```

## 四、AI 判断流程

```yaml
AI 在探索完成后执行以下判断：

  1. 加载探索结果:
     - 读取 discovery_gaps 数组
     - 读取每个发现页面的元素信息（按钮、弹窗、表单字段、菜单链接）
     - 读取原始需求/spec 中的业务模块范围

  2. 相关性过滤（核心步骤）:
     对每个候选补充目标，依次回答三个问题:
       Q1: 这个弹窗/功能/链接是否位于需求目标页面或其直接子页面（通过菜单/按钮/弹窗可达）？
         判断标准: 从需求目标页面出发，通过 1 次点击或 1 次弹窗打开的页面/功能。
         例: 需求页面是"合作方开票信息"→ 页面上的"新增付款单位"弹窗 → 是（在目标页面弹窗中）
         例: 需求页面是"合作方开票信息"→ 侧边栏"用户管理"（不同模块的导航入口）→ 否
         例: "新增"弹窗内的"选择客户"下拉 → 链接到客户选择页面 → 是（弹窗内可达）

       Q2: 这个弹窗/功能/链接的操作结果是否影响需求目标页面的验证？
         例: "批量导入"会影响列表数据 → 影响列表展示验证 → 是
         例: "更换主题"不影响数据链路 → 否

       Q3: 这个弹窗/功能是否包含需要验证的交互逻辑（表单/校验/状态变更）？
         例: 新增弹窗有表单校验 → 有 → 补充
         例: 纯展示弹窗无任何交互 → 无 → 跳过

  3. 分级补充:
     强制补充（至少 P1）— 满足 Q1+Q2+Q3:
       - 需求目标页面的 CRUD 弹窗/功能
       - 需求链路中的状态流转操作
       - 与需求功能有直接数据关联的配置项

     建议补充（P2）— 满足 Q1+Q3 但不满足 Q2:
       - 需求页面的非核心 Tab/子功能
       - 弹窗中有额外字段但非关键字段

     不补充:
       - Q1 不满足 → 直接跳过
       - 发现元素与已有用例完全对应 → 去重跳过
       - 单次探索最多补充 20 条（熔断）

  4. 生成补充用例:
     - 按 case-template.md 字段定义生成
     - 标注"来源依据 = 探索发现"（区别于"当前新需求"）
     - 标注"影响说明 = 探索发现{X弹窗/功能}，与{需求模块}相关，初始用例未覆盖"
     - 用例 ID: TC-{模块缩写}-SUP-{序号} 或 APP-{模块缩写}-SUP-{序号}

  5. 合并用例集:
     - 初始用例集 + 补充用例集 → 完整用例集
     - 重复检测 → 保留更详细的那条
```

## 五、示例：相关性判断

```yaml
场景 A — 应该补充:
  需求: "合作方开票信息管理 — 列表页展示和搜索"
  探索发现:
    - 列表页"新增付款单位"按钮 → 弹出新增表单弹窗
      → Q1: 属于开票信息管理模块？是
      → Q2: 新增操作影响列表展示验证？是（新增后列表变化）
      → Q3: 弹窗有表单字段需要验证？是
      → 结果: ✅ 补充 TC-PI-SUP-001 新增-正常创建, TC-PI-SUP-002 新增-必填校验
    - 列表页"开票记录"Tab → 切换到开票记录子页面
      → Q1: 属于开票信息管理模块？是（开票记录是开票信息的一部分）
      → Q2: 影响需求验证？是（开票记录与开票信息有关联）
      → Q3: 页面有交互功能？是（列表、搜索、导出）
      → 结果: ✅ 补充开票记录页面的基础展示+搜索用例

场景 B — 不应补充:
  需求: "合作方开票信息管理 — 列表页展示和搜索"
  探索发现:
    - 侧边栏"用户管理"菜单 → 链接到用户管理页面
      → Q1: 属于开票信息管理模块？否（用户管理是独立模块）
      → 结果: ❌ 跳过
    - 底部"帮助中心"链接 → 链接到帮助页面
      → Q1: 属于开票信息管理模块？否
      → 结果: ❌ 跳过
    - 页面顶部"系统通知"弹窗 → 纯信息展示
      → Q3: 有交互逻辑需要验证？否
      → 结果: ❌ 跳过

场景 C — 混合判断:
  需求: "书籍详情页 — 加入书架功能验证"
  探索发现:
    - 详情页"开始阅读"按钮 → 跳转阅读器
      → Q1: 属于加入书架相关？是（详情页功能，但不在需求范围）
      → Q2: 影响加入书架验证？否（开始阅读不直接影响加入书架结果）
      → Q3: 有交互？是
      → 结果: 建议补充（P2），阅读器启动是详情页耦合功能
    - 侧边栏"福利中心"菜单 → 福利中心页面
      → Q1: 属于加入书架相关？否
      → 结果: ❌ 跳过
```

## 六、探索的递归深度与边界

```yaml
递归探索规则:
  深度 1（需求目标页面）:
    - 全面探索：所有按钮、链接、Tab、表单
    - 记录所有发现的入口（弹窗打开、菜单链接）
    - 相关性过滤: 弹窗/模态框 → 探索表单内容，链接/菜单 → 仅记录，不追踪

  深度 2（弹窗/模态框内部）:
    - 探索弹窗内的所有表单字段和交互元素
    - 不追踪弹窗内的链接到新页面（结束递归）
    - 记录字段清单 + 缺失字段

  深度 3（同模块子页面）:
    - 仅当子页面与需求模块强相关时才追踪（满足 Q1+Q2）
    - 同模块子页面的全面探索
    - 深度 3 为最大深度

  停止条件:
    - 页面是外部链接（跳转到第三方域名）→ 停止
    - 页面是下载链接 → 停止
    - 页面是帮助/关于/隐私政策/用户协议等非业务页面 → 停止
    - 页面需要特殊权限（超出测试范围）→ 停止
    - 已探索过相同 URL/页面标识（防止循环）→ 停止
    - Q1 不满足（与需求模块无关）→ 停止
```

## 八、与各平台探索的关系

```yaml
Web 平台:
  - 探索输出: exploration_result.json（含 discovery_gaps）
  - 反馈链路: web/exploration.md → 产出 → common/discovery-feedback.md → phase1-analyze.md § 1.4
  - 补充用例后: 合并到 test_cases.json → Phase 3b 执行

iOS 平台:
  - 探索输出: ios_exploration_result.json（含 discovery_gaps）
  - 反馈链路: ios/exploration.md → 产出 → discovery-feedback.md → phase1-analyze.md § 1.4
  - 补充用例后: 合并到 test_cases.json → Phase 3b 执行

Android 平台:
  - 探索输出: android_exploration_result.json（含 discovery_gaps）
  - 反馈链路: android/exploration.md → 产出 → discovery-feedback.md → phase1-analyze.md § 1.4
  - 补充用例后: 合并到 test_cases.json → Phase 3b 执行

混合模式:
  - Web 探索 → 发现与需求相关的配置弹窗 → 补充 Web 用例（配置操作）
  - APP 探索 → 发现与需求相关的展示页面 → 补充 APP 用例（验证展示）
  - 跨平台关联: 如果 Web 补充了配置用例 → APP 也需要补充对应的验证用例
```

## 九、熔断保护

```yaml
补充用例的熔断:
  - 单次探索最多补充 20 条用例（防止过度补充）
    配置项: MAX_SUPPLEMENT_CASES = 20
    熔断触发后: 提示用户 "已发现 N 个可补充场景（上限 20），已生成 20 条。是否继续补充剩余 X 条？"
    → 用户确认 → 继续补充 | 用户拒绝 → 保留已生成的 20 条
  - 补充的用例优先级最低为 P2（P3 级别的场景不补充，避免噪音）
  - 如果探索发现 5+ 个满足相关性但未覆盖的页面 → 暂停，提示用户确认是否全部补充
  - 补充的用例如果 80% 以上标记为 FAIL → 检查是否环境问题导致误判
```
