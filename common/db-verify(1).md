# DB 验证 — AI 驱动数据库完整性校验

## 定位

AI 自主探索数据库结构，推导验证点，执行验证。**不预设表名、字段名、SQL 模板**。

## AI 判断框架

```yaml
# AI 在验证 DB 时自动执行以下流程：
1. 理解业务场景:
   - 从当前测试的页面/功能理解"这个操作会影响哪些数据"
   - 示例：新增一条记录 → 应该影响"该表的数据行数+1"
   - 示例：修改状态 → 应该影响"该记录的 status 字段"

2. 探索数据库:
   - SHOW TABLES LIKE '%{关键词}%' 定位目标表
   - DESC {table} 获取列信息
   - AI 根据列名和类型判断"哪些字段与当前操作相关"

3. 推导验证点:
   - 新增操作 → 验证行数增加 + 各字段值正确
   - 修改操作 → 验证字段值变更 + 变更时间/操作人记录
   - 删除操作 → 验证行数减少 + 关联数据完整性
   - 状态流转 → 验证状态值 + 操作人/时间字段
   - 计算字段 → 验证计算结果与实际值一致

4. 执行验证:
   - AI 根据推导结果编写 SQL
   - 执行并判断结果是否符合预期
   - 不符合 → AI 分析原因（数据未写入？字段名猜错？业务逻辑有 Bug？）
```

## AI 验证原则

```yaml
原则:
  - 单次连接: AI 复用已有 DB 连接，不重复 connect/close
  - 不预设: AI 不预设任何表名/字段名，全部通过 DESC 探查
  - 安全: SELECT 为主，不修改生产数据（绕过操作除外）
  - 大表: 超过 10000 行的表自动加 LIMIT
  - 自适应: 如果 DESC 发现表结构不符合预期，AI 自动调整验证策略
  - 事务保护: 仅用于验证，不开启写事务；如涉及造数绕过，必须先 snapshot 再操作，支持逆向 SQL 回滚
```

## 事务保护机制

```yaml
# 当 DB 验证涉及数据修改（造数绕过场景）时：
事务保护流程:
  1. 操作前快照:
     - 记录当前数据状态（关键字段值、行数）
     - 保存到 verification_snapshot.json
     - 记录时间戳和操作描述

  2. 执行修改:
     - 仅在测试环境执行
     - 记录执行的 SQL 语句
     - 记录受影响行数

  3. 验证恢复:
     - 执行逆向 SQL 回滚（DELETE/UPDATE 恢复原值）
     - 验证数据是否恢复到修改前状态
     - 如回滚失败，记录警告并通知用户

  4. 异常处理:
     - 修改过程中发生错误 → 立即执行回滚
     - 回滚失败 → 标记为环境问题，停止相关验证
```

## AI 输出格式

```yaml
# AI 自动生成验证报告：
验证报告:
  - 验证项: "新增记录字段完整性"
  - 目标表: "invoice" (AI 通过关键词匹配定位)
  - 验证方式: "SELECT * FROM invoice ORDER BY id DESC LIMIT 1"
  - 结果: PASS
  - 说明: "新增记录的 8 个字段值与页面输入一致"
  - 异常: null

  - 验证项: "状态流转完整性"
  - 目标表: "invoice_audit_log" (AI 通过关联关系定位)
  - 验证方式: "SELECT status, operator, operate_time FROM invoice_audit_log WHERE invoice_id=X"
  - 结果: FAIL
  - 说明: "status=5 的记录缺少 operator 字段"
  - AI 分析: "可能是代码未记录操作人，建议检查保存逻辑"
```
