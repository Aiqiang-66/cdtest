# iOS 执行引擎 — 混合驱动版（含交互探索）

## 定位

**两阶段执行**：先执行交互探索（发现所有页面元素），再执行用例循环（验证具体功能）。

探查策略、等待策略、加载判断等详细优化见 `common/execution-optimization.md`。
探索发现→用例补充反馈链路见 `common/discovery-feedback.md`。

## 一、固定执行循环（不可跳过）

```yaml
# 每个用例按以下循环执行：
执行循环:
  步骤 1: 探查页面 → 获取 APP 当前页面状态（探查策略见 execution-optimization.md §一）
  步骤 2: AI 理解页面 → 判断当前页面是什么
  步骤 3: AI 选择操作 → 根据用例步骤选择操作
  步骤 4: 执行操作 → tap / send_keys / swipe
  步骤 5: 等待响应 → 等待页面变化（等待策略见 execution-optimization.md §二）
  步骤 6: 验证结果 → 探查页面验证（加载判断见 execution-optimization.md §三）
  步骤 7: 记录结果 → PASS/FAIL + 截图
  步骤 8: 下一个用例 → 回到步骤 1
```

## 二、AI 决策点

```yaml
# AI 在循环中的决策点：
决策点 1（步骤 2）: 理解页面
  - 当前页面是什么？（Tab 页/列表页/详情页/弹窗）
  - 页面是否加载完成？（参考 execution-optimization.md §三 iOS 加载信号）
  - 是否有异常？（Alert/闪退/空白页）

决策点 2（步骤 3）: 选择操作
  - 根据用例步骤在 page_source 中找到目标元素
  - 通过元素 label/name/type 定位
  - 选择操作类型（tap/send_keys/swipe）
  - 判断是否可以合并探查（参考 execution-optimization.md §一 探查触发条件）

决策点 3（步骤 5）: 等待响应
  - 根据操作类型选择等待策略（参考 execution-optimization.md §二 等待策略）
  - 根据页面复杂度/网络状况调整等待时间
  - 超时 → 高成本探查 → 判断是否继续等待

决策点 4（步骤 6）: 验证结果
  - 是否出现预期元素/文本？
  - 页面是否跳转？
  - 是否有 Alert/弹窗？
  - 参考 execution-optimization.md §三 加载完成判断
```

## 三、元素交互模式（固定类型 + AI 定位）

```yaml
# 固定交互类型：
交互类型:
  - tap: 点击按钮/标签/列表项
    → AI 在 page_source 中找到目标元素 → tap
    → 探查成本: 导航类=高成本, 非导航类=中成本
  - send_keys: 输入文本
    → AI 找到 TextField/SecureTextField → tap → send_keys
    → 探查策略: 跳过探查，合并到后续操作
  - swipe: 滑动
    → AI 判断方向（上/下/左/右）→ swipe
    → 探查策略: 选择性探查（只探查新加载区域）
  - long_press: 长按
    → AI 找到目标元素 → long_press（时长 AI 判断）
    → 探查成本: 中成本

# AI 定位方式：
AI 定位:
  - 优先通过 label 匹配（元素的文本标签）
  - 其次通过 name 匹配（元素的名称属性）
  - 最后通过 type 匹配（Button/TextField/StaticText）

# 操作验证适应循环（固定）:
操作循环:
  每次操作后必须: 验证结果 → 检查是否达到预期
  - 成功 → 继续下一步
  - 失败 → 换方式重试（最多 3 次）:
    1. 重新获取 page_source → 确认元素状态
    2. 换定位方式（label → name → type）
    3. 换操作方式（tap → 坐标点击）
  3 次仍失败 → 标记失败

# 交互卡住跳过机制（防死循环）:
防卡住:
  - 同一操作失败 ≥ 3 次 → 不再重试相同方式，按层级升级
  - 单步骤耗时 > 3 分钟 → 强制跳过，标记 SKIP
  - 连续 5 次 page_source 无变化 → 刷新/重启 APP
  - 详细规则见 common/execution-optimization.md §场景 13
```

## 三.五、APP 列表/内容动态加载等待

```yaml
# APP 端列表/内容加载通常需要 3-15 秒，固定等待不可靠：
APP 加载等待流程:
  1. 操作触发数据加载（点击 Tab / 搜索 / 刷新）
  2. 轮询检测加载完成（每 1.5 秒一次）:
     检测信号:
       - ActivityIndicator 消失（iOS 正向信号）
       - 目标 Cell/Row 元素出现
       - NavigationBar title 稳定
       - 列表底部 "加载更多" 或分页控件出现
       - "暂无数据" / "Empty" 提示出现（空状态）

  3. 停止条件（任一满足即停止轮询）:
     - 数据行出现 + ActivityIndicator 消失 → 加载完成
     - 空状态提示出现 + ActivityIndicator 消失 → 空数据
     - 超时 20 秒 → 高成本 page_source 探查诊断

  4. 超时后诊断:
     - page_source → AI 判断:
       - 页面白屏/空 → 可能是网络问题或 APP 卡死
       - "加载中" 持续 → 环境问题，重启 APP 重试
       - "暂无数据" → 有效状态（可能是空列表）

超时阈值:
  简单列表（少量静态数据）: 8 秒
  网络加载列表（API 请求）: 15 秒
  图片/富媒体列表: 20 秒
  首次加载（无缓存）: 超时 × 2
```

## 四、异常处理（固定策略 + AI 判断）

```yaml
# 固定异常处理策略：
异常处理:
  - 元素未找到:
    1. 重新获取 page_source（高成本探查）
    2. 再找（最多 3 次）
    3. 仍找不到 → 标记失败
    AI 判断: 是页面未加载？还是元素确实不存在？

  - Alert 弹窗:
    1. 自动处理（接受/拒绝）
    2. 继续执行
    AI 判断: 弹窗是否影响当前操作？

  - 交互卡住:
    1. 同一操作步骤失败 ≥ 3 次 → 检查是否卡在同一个交互模式
    2. 单步骤耗时 > 3 分钟 → 强制跳过
    3. 跳过当前用例 → 标记 SKIP + 记录详细跳过原因
    4. 清理状态（关闭弹窗/返回上级页面）→ 继续下一条独立用例
    → 详细规则见 common/execution-optimization.md §场景 13

  - APP 闪退:
    1. 重新启动 APP
    2. 重试（最多 2 次）
    3. 仍闪退 → 标记环境问题
    AI 判断: 是 APP 崩溃？还是设备问题？

  - 页面超时:
    1. 高成本探查（诊断当前状态）
    2. 如果页面已加载（只是慢）→ 继续执行
    3. 如果页面未加载（卡死）→ 重启 APP → 重试（最多 2 次）
    4. 仍超时 → 标记环境问题
    AI 判断: 是网络问题？还是 APP 卡死？
```

## 四.一、APP 异常场景清单（必须覆盖）

```yaml
# 每个功能点的测试用例中，必须包含以下异常场景：

必测异常场景:
  列表/内容展示类:
    - 空数据: 清空数据源后进入页面
      → 验证: 显示空状态占位图/提示文本，无白屏/闪退
    - 超大数据量: 加载超过 100 条的数据列表
      → 验证: 滚动流畅不卡顿，分页/懒加载正常工作
    - 快速切换 Tab: 快速连续点击不同 Tab
      → 验证: 数据正确切换，无界面重叠/错乱

  搜索/输入类:
    - 不存在的结果: 搜索不可能存在的关键词
      → 验证: 显示"无搜索结果"友好提示
    - 空搜索: 输入框为空时点击搜索
      → 验证: 显示全部数据或提示输入关键词
    - 特殊字符: 输入 emoji/特殊符号
      → 验证: 不崩溃，正常过滤或提示

  网络异常类:
    - 飞行模式: 开启飞行模式后进入需联网的页面
      → 验证: 显示网络异常提示，不白屏/闪退
    - 弱网: 限速环境下操作
      → 验证: 加载超时后有重试入口或友好提示
    - 网络恢复: 飞行模式 → 关闭飞行模式
      → 验证: 自动重连或手动刷新后正常加载

  中断场景:
    - 来电中断: 操作中接听电话
      → 验证: 返回 APP 后回到中断前的页面，数据不丢失
    - 后台切换: 操作中切到后台再切回来
      → 验证: 页面状态保持，无数据丢失/闪退
    - 横竖屏切换: 旋转设备
      → 验证: 布局自适应，无元素错位

  权限场景:
    - 拒绝权限: 拒绝位置/通知/相册等权限
      → 验证: 相关功能有权限引导，不闪退
    - 权限恢复: 从系统设置中开启权限后返回 APP
      → 验证: 功能恢复正常
```

深度测试矩阵引用:
  见 common/execution-optimization.md §七 — L1(UI可见性) / L2(功能正确性) / L3(数据正确性) / L4(组合联动正确性)
  每个功能点必须覆盖对应等级的验证深度，防止"只探查不测试"。
```

## 七、人工协助阻塞处理

```yaml
阻塞场景:
  - Appium 无法操作的 Native 弹窗（如 iOS 系统权限对话框）
  - 需要手动扫码/录入的设备绑定流程
  - 需要接收并输入短信/邮箱验证码
  - Capabilities 配置缺失导致无法启动 APP

处理流程:
  1. 报告用户: 说明阻塞原因 + 需要用户做什么
  2. 请求 5 分钟内协助
  3. 5 分钟后未反馈 → 标记"⏭️ 跳过（人工协助超时）", 记录原因
  4. 禁止: ❌ 不告知用户静默跳过 / ❌ 无限期等待
```
