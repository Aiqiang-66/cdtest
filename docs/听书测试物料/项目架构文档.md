## 一、业务与交付物

**听书 TTS** 把书籍章节正文（`read_content`）合成为有声书音频。测试要回答的问题不是"接口返回 200 了吗"，而是三件事：

1. **文案有没有丢**（听书业务最怕漏字）；
2. **音频能不能听、能不能用**（削波、静默空洞、时长、可获取性）；
3. **长时间高并发下稳不稳**（成功率、延迟趋势、卡死）。

一次调用交付的是**一条产物链**，而不是一个结果码：

```
read_content ──切句/分段──> 分段合成 ──编码──> MP3（落 COS）──> audio_url（时效签名）
                                          └──> metadata.json / SRT ──> metadata_url（时效签名）
```

## 二、被测系统架构（服务端）

### 2.1 链路与接口

| 环节 | 说明 |
|---|---|
| 建任务 | `POST {BASE}/Video/CreateUniversalTransparent`，`taskType=74`，业务参数放在 `ext`（JSON 字符串） |
| 鉴权 | `sign = base64(HMAC-SHA256(SECRET_KEY, 原始 body))`，请求头 `sign` |
| 轮询 | `POST {BASE}/Task/GetAllTaskStatus`，入参 `{"taskType":74,"taskIds":[...]}` |
| 状态 | **`2`=成功**（`data.audio_url` / `data.metadata_url`）· **`3`=失败** · **`67`=处理中** |
| 环境 | 测试 `https://ai-main-none-dev.changdu.ltd`｜生产 `https://ai-main-none.changdu.vip` |

`ext` 关键字段：

| 字段 | 说明 |
|---|---|
| `read_content` | 章节正文（**必须保留段落换行**，见 §3.2 M0） |
| `chapter_title` | 章节标题（返回中作为 `paraIndex=-1` 的标题段） |
| `model` | `higgs`（当前在用的 TTS 模型） |
| `lang` / `voice` | 语种与音色，如日语 `9`/`Japanese_female`、韩语 `14`/`Korean_female`（取值表见 `docs\听书测试物料\语言参数`） |

### 2.2 服务端处理链（黑盒视角）

```
建任务(签名校验/参数解析)
   └─ 入队（并发槽位/优先级）
        └─ 切句与分段（按段落 → 句 → 字幕段；决定 paraIndex 与时间轴）
             └─ 分段合成（TTS）──> 失败片段处理（重试 / 静默占位 ← 已知缺陷）
                  └─ 编码 MP3（ffmpeg 封装，24 kHz / 单声道 / ≈51 kbps VBR）
                       └─ 上传 COS（audio / metadata 分桶、分地域）
                            └─ 状态置 2（★ 已知：置成功与对象可读之间存在竞态）
```

### 2.3 产物特征（实测基线，可用于断言）

| 项 | 实测值 |
|---|---|
| 编码 | MP3，**24 kHz / 单声道 / ≈51 kbps VBR**；容器标签 `encoder=Lavf60.16.100`，无 ID3 标题 |
| 体积 | 5000 字任务 ≈ 3.9~4.9 MB，时长 ≈ 12~13 分钟 |
| 时长一致性 | 音频时长 vs metadata 末段 `endMs` 差 ≤80 ms |
| 音频存储 | COS 香港桶，路径可预测：`audiobook/<taskId>.mp3` |
| metadata 存储 | COS 广州桶，带 `q-sign` 时效签名（过期后需重新查询取新链接） |

## 三、测试框架架构

### 3.1 设计原则

1. **单一事实源**：所有口径、必测项、流程、红线只写在 `SKILL.md`，脚本与文档都引用它，避免多处定义漂移。
2. **证据优先**：每个结论必须能从磁盘上留下的原始产物复现（`src/meta/srt/audio/tasks.jsonl/summary.json/analysis/`）。
3. **口径分离**：文本口径判"漏字"、ASR 口径看"听感"、质量口径量"波形"——**三者不可互相替代**。
4. **前置于测试**：语料不合规（M0 不通过）直接不开跑，避免用错误输入得出的结论污染历史。

### 3.2 必测项（每轮都要查）

| 项 | 内容 | 判定线 |
|---|---|---|
| **M0** | 语料门禁：正文必须保留段落换行 | 每单元多段落；`distinct paraIndex > 1`；不通过不得开跑 |
| **M1** | 文案一致性（**唯一判漏口径**） | 下发 `read_content` ↔ metadata 正文段，缺失字 = 0 |
| **M2** | 音频质量 | 峰值 ≤0.999；无 >3s 且 metadata 有文本的长空洞；人工听测签字 |
| **M3** | 漏词/准确率 | 文本口径为准；ASR（large-v3）删除率仅参考 |
| **M4** | 切句 | 无超长段（>200 字）；无不可能语速（>15 字/秒） |
| **M5** | 字幕完整性 | 空字幕 0；`SRT 条目 ≠ segments` 0；无 paraIndex 缺口（**每次必查**） |

### 3.3 测试阶段（Phase）

| 阶段 | 内容 |
|---|---|
| 1 | 环境检查（服务可达、密钥、依赖） |
| 2 / 2.5 / 2.6 | 功能正确性 / 文案一致性（文本口径）/ 切句质量与完整性（M4） |
| 3 | 准确率（WER/CER，ASR） |
| 4 | 性能与稳定性（按需求选：并发档、时长、24h 浸泡等） |
| 5 / 5.5 | 音频质量（M2）/ 字幕完整性与时间轴（M5） |
| 6 | 字幕 vs 文本对比 |
| 7 | 模型对比 |
| 8 | 语义与停顿专项 |
| **9** | **产物与分发**（MP3 本体、COS 链接、任务生命周期；见 `测试用例\接口与MP3产物_补充测试场景.md`） |

### 3.4 脚本流水线

```
① 语料准备        build_ja_ko_5000char_material.py    → material/units.jsonl + unit_*.txt（保留段落）
② 接口用例        run_text_format_cases_0924.py       → mp3/文案格式用例_*/{src,meta,results.json}
③ 跑批（性能/稳定）run_higgs_ja_ko_10concurrent_30min.py → mp3/<批次>/{src,meta,srt,audio,tasks.jsonl,summary.json,progress.log}
④ 分析            analyze_ja_ko_perf_0924.py          → <批次>/analysis/perf_m1_m5.json（性能+M1+M5）
                  audio_quality_ja_ko_0924.py         → <批次>/analysis/audio_m2.json（削波/响度/空洞/补齐）
                  asr_accuracy_ja_ko_largev3_0924.py  → mp3/analysis_ja_ko_asr_m3/asr_*.json（M3 抽样）
⑤ 报告            gen_report_round2_summary_0924.py   → 测试报告/日韩_接口与稳定性_总报告_*.md
                  gen_report_stability_0924.py        → 稳定性专项报告
                  gen_report_cases_0924.py            → 接口用例报告
⑥ 交付            export_dev_pack_round2_0924.py      → 开发分析包（台账+证据+音频片段+复现脚本，打包 zip）
⑦ 留档            scripts\sync_tingju_skill_to_git.ps1 -DryRun / -Push（白名单+守卫+隔离索引）
```

## 四、数据模型

### 4.1 批次目录（跑批产物，自解释、可复现）

```
docs\听书测试物料\mp3\<批次名>\
├── material\units.jsonl + unit_*.txt   # 本批使用的语料（M0 合规；新目录必须自带）
├── src\task_0001.txt                   # 实际下发的 read_content（M1 的前提）
├── meta\task_0001.json                 # 接口返回的 metadata 原文
├── srt\task_0001.srt                   # 由 metadata 生成的输出字幕
├── audio\task_0001.mp3                 # 产物音频留证
├── tasks.jsonl                         # 逐任务台账（指标+文案比对结果）
├── summary.json                        # 汇总统计
├── progress.log                        # 运行日志（★ 后台跑批看进度看这里）
└── analysis\                           # 分析产物（perf_m1_m5.json / audio_m2.json / asr/ / 听测清单）
```

### 4.2 `tasks.jsonl` 关键字段

| 字段 | 含义 |
|---|---|
| `seq` / `unit` / `taskId` | 任务序号 / 语料单元 / 接口任务号 |
| `ok` / `status` / `elapsed_s` | 是否成功 / 状态码 / 端到端耗时 |
| `chars` / `missing_chars` / `missing_char_ratio` | 下发字数 / M1 缺失字数 / 缺失率 |
| `seg_chars_median` / `max_seg_chars` / `n_seg_gt200` | 段长中位 / 最长段 / 超长段数（M4） |
| `n_seg_rate_gt15` / `n_seg_rate_lt2` | 高语速段 / 疑似静默段 |
| `audio_bytes` / `audio_url_present` | 音频体积（**440 B 即 COS 错误页**）/ 是否返回链接 |

### 4.3 metadata（接口返回）与 SRT

- metadata 是**段列表**：每段含 `paraIndex`（段落序号，标题段为 `-1`）、`startMs/endMs`（时间轴）、`text`、`offset`（段内/段落内字符偏移）；
- SRT 由 metadata 生成：**SRT 条目数应等于字幕段数**（同句可拆多段，不是 1:1 对应切句）；
- **时间轴**是已知风险点（见 §7 缺陷 5），不要默认它可信。

## 七、已知缺陷基线（避免重复报告，但每轮回归）

| # | 缺陷 | 级别 | 现象与证据 |
|---|---|---|---|
| 1 | 参数校验缺失 | P1 | 空文本 / 纯空白 / `lang=999` 均返回成功并产出音频（用例 A04a/A04b/A10） |
| 2 | 任务卡死 `status=67` | P1 | 跨小时仍 67、`data` 空、`errorCode=0`、产物 404（日语 3/82、韩语 2/98 复现；最久挂 9 小时） |
| 3 | 产物可见性竞态 | P1 | 任务成功后**立即**拉 `audio_url` 得 **440 B** COS 错误页；延迟重下 100% 成功（18/225 与 14/176 两次复现） |
| 4 | 日语静默空洞 | P1 | metadata 有文本、音频 **81.64 s** 固定时长无声；M0 合规语料下仍复现 |
| 5 | 段级时间轴不可信 | P2 | 69 字只给 0.56 s（>15 字/秒 段占 1.3%）；ASR 定点核查显示时间轴错位 |
| 6 | 日语削波/响度越界 | P2 | 峰值 max ≈1.22、RMS ≈−11.5 dBFS（日语批次全量触顶） |
| 7 | 韩语内容缺失（历史） | P1 | 0924 扁平语料下 16 个任务缺口 20~46%；**M0 合规语料下未复现** → 与段落结构强相关 |

## 八、扩展指南
