| 口径 | 比对对象 | 能发现 | 不能发现 | 对应 Phase |

## ⛔ 测试前置必做（M0：语料必须保留原文段落换行）★ 不通过不得开跑

> **M0 是硬性前置条件：语料格式不对，后面所有结论都不可信。**
> 实测教训（2026-09-24 日语 94 任务、韩语 130 任务两批压测）：把整章句子拼接成**单段落**下发 →
> 服务端拿不到段落结构（**`paraIndex` 恒为 0**）→ 切句/分段退化 →
> **超长段（最长 1757 字）**、**不可能语速（最高 277 字/秒）**、**81.64s 固定时长静默占位**、
> 韩语 **16/130 个任务音频缺失 20~46%**（整段 ASR 实测 0040 缺 34.55%、0071 缺 45.97%，
> 其中超长段丢失 76~90%）——而 **M1 文本口径仍显示 0 缺失，把问题完全掩盖**。

**规则：下发文本必须保留原文的段落结构（换行），严禁把整章/整节拼成一个段落。**

| 项 | 要求 |
|---|---|
| 段落保留 | 原书/原稿的段落边界必须保留为换行 `\n`；同一段内的原有空格不要擅自增删 |
| 段落长度 | 原文单段过长可再拆，但**不得把多个段落合并** |
| 禁止写法 | `" ".join(sentences)`、`re.sub(r"\s+", " ", text)`、`text.strip()` 前先 `replace("\n"," ")` 之类**抹平换行**的做法 |
| 内容一致性 | 去掉所有空白后必须与源文一致（内容 0 丢失），但同时**换行数量/位置要保持原文结构** |
| 两种等效写法 | ①逐段一行（段落间单换行）；②段落之间留空行 —— 都算保留了段落结构，**只要不合并段落** |

> 它也是最容易被漏的一项：任务 `taskStatus=2`（成功）、音频也生成了，**但字幕就是少了几条**，
> 只看成功率与音质完全发现不了。
>
> **M5 与 M1/M4 的分界**（三者互不替代，都要跑）：
> | 项 | 看什么 | 口径 | 典型失守现象 |
> |---|---|---|---|
> | M1 | 文本**内容**有没有丢 | `read_content` vs metadata **拼接文本**的词对齐 | 文案词少了 |
> | M4 | 切句**切得对不对** | 切句方案输出 | 超长句、碎片、截断、乱序 |
> | **M5** | 字幕**条目/文件全不全** | metadata **条数/结构** + SRT 文件 + 时间轴 | 条数对不上、空字幕、时间轴空洞、SRT 漏条目 |

> #### 「丢字幕」和「丢文案」是同一个问题吗？——**高度重叠，但不等价，必须都测**
>
> 字幕就是 metadata 的 segments，所以**多数情况下同一根因会同时表现为两者**。
> 实测 0910 那批（同一本书同一章）：
>
> | | segments 条数 | paraIndex 缺口 | 正文词数 |
> |---|---:|---:|---:|
> | 丢失批次 | 357 | 30 | 1395 |
> | 干净复跑 | 388 | 0 | 1519 |
> | **差值** | **31** | — | **124** |
>
> 报告记录的正是「缺失块 31 / 缺失词 124」——**31 条 segment 被丢弃，同时等于"少 31 条字幕"和"少 124 个词"**。
> 这次是同一根因的两种观测口径。
>
> **但存在只有一方失守的通道，所以不能互相替代：**
>
> | 情形 | 丢文案(M1) | 丢字幕(M5) |
> |---|:--:|:--:|
> | metadata segment 被静默丢弃（0910 那批） | ✅ | ✅ |
> | 一句拆成多条字幕（实测 `paraIndex=230`） | ❌ | 条数**变多**，正常非缺陷 |
> | 空字幕段（text 为空） | ✅ | ✅ |
> | SRT 派生时丢/多条目（俄语实测 metadata 359 vs SRT 360） | ❌ | ✅ |
> | text 被截断/改写但条数不变 | ✅ | ❌ |
>
> **结论**：只看 M1 会漏掉「SRT 派生漏条目」「时间轴空洞」；只看 M5 会漏掉"条数没变但文本被截断"。
> **两者都要跑。**

> **为什么 M4 也是必测**：切句是「文本 → TTS」的**上游关口**。
> 切句丢内容 → 直接表现为 M1 的「切句层丢文案」；切句切出超长句/碎片 → 直接引发
> 合成失败、漏词与音频破音/断续。**M1 查到缺失却定不了因时，答案通常就在 M4。**
> 且 M4 是本地执行、秒级完成，成本极低。

**M1 的并发口径要求（低并发与高并发都要做）：**

| 并发档 | 目的 | 做法 |
|---|---|---|
| **低并发（1~2）** | 排除排队干扰，看"干净链路"下是否一致 | 串行/低并发下发 N 个任务，逐任务比对 |
| **高并发（达到服务上限，如 5/16）** | 暴露并发竞争导致的丢文案 | 并发打满持续下发，逐任务比对 |

> 历史证据：文案丢失**只在并发下出现过**（0910 五并发批次英语 8.06% / 德语 10.16% / 俄语 7.63%），
> 单发/串行从未复现。**因此只做低并发或只做高并发都不算完成 M1。**

**M2 的判定必须"客观指标 + 人工听测"双管：**

| 手段 | 查什么 | 门槛 |
|---|---|---|
| 客观波形 | 峰值/削波样本数、RMS/响度、高频占比、底噪、异常静音 | 见 Phase 5 TC-AUD-006~010 |
| **人工听测** | 破音/爆音、杂音/齿音/嘶嘶声、卡顿、漏读 | **必须由人听**，波形指标不能替代 |

> ⚠️ 历史教训：客观指标"通过"不等于人工听测"通过"。0824 两份报告对**英语**给出**相反结论**——
> 一份客观波形报告称"英语未发现问题（峰值 ≤0.994）"，另一份结论表称"英语不通过：发现存在爆音、杂音"。
> **两份结论冲突时，一律以人工听测复测为准**，且必须在报告中说明冲突。

### Phase 2.5: 输入/输出文案一致性测试（纯文本口径）★ 每轮必做

**测试目的**：验证「下发的 `read_content`」与「接口返回 metadata 的文本（即字幕文本）」逐词一致，发现服务端丢句/丢词/串任务。

> 本阶段**完全不涉及 mp3、ASR、Whisper**。只看文本就能定论，成本极低、结论确定，应作为每轮下发的**第一个卡点**。

#### 判定口径

| 项 | 定义 |
|----|------|
| 归一化 | NFKC → 统一引号 → 去首尾标点 → 小写 → 按空白切词 |
| 缺失词 (missing) | 词序列对齐中 `delete` / `replace` 左侧（输入有、输出无）= **漏文案** |
| 多余词 (extra) | `insert` / `replace` 右侧（输出有、输入无），用于识别串任务 |
| 缺失率 | 缺失词 / 输入词 |
| 相似度 | `difflib.SequenceMatcher.ratio()` |

#### 通过标准（门禁：不达标即判 FAIL）

| 指标 | 目标 | 说明 |
|------|------|------|
| 整体缺失率 | **0.000%** | >0 即不通过，不允许用"平均值正常"掩盖个别任务丢失 |
| 单任务缺失词 | **0** | 任一任务 >0 即记录并人工复核 |
| 去标点后逐字符一致 | **100%** | 未达 100% 说明存在真实内容差异 |
| 压缩空白后逐字符一致 | 允许 <100% | 差异若全部来自标点写法（见踩坑项 4）可放行 |

> **凡缺失词 > 0 的任务一律判不通过，不做"少量可接受"的妥协。** 文案缺失是功能性缺陷，不是性能波动。

#### 双通道检测法（两通道都要跑，互为独立证据）

**通道 A —— 词对齐（主口径）**
输入词序列 vs 输出词序列做 `difflib.SequenceMatcher`，统计 `delete` / `replace`。
- 前提：**必须保存下发原文**。下发脚本需把每任务的 `read_content` 落盘（`src/task_XXXX.txt`）。

**通道 B —— `paraIndex` 连续性（免原文，用于交叉验证）**
服务端为每句分配全局递增 `paraIndex`，**序号缺口 = 该句从未被输出**：

```python
pas  = sorted(s["paraIndex"] for s in segs if s["paraIndex"] >= 0)
gaps = [i for i in range(min(pas), max(pas) + 1) if i not in set(pas)]   # gaps 数量即丢失句数
```

- 实测缺口数与通道 A 的缺失块数**一一对应**（30/36/28 vs 31/35/29），可作独立佐证。
- 仅适用于**整章**下发；分段/滑窗下发时序号会重置，不适用。

**两通道结论不一致时以通道 A 为准**，通道 B 用于定位与交叉验证。

#### 丢失去向定界（生成层 vs 切句层）

| 通道 A | 通道 B | 结论 |
|--------|--------|------|
| 有缺失 | 有缺口 | **生成/分段合成层丢句**（句子进了流水线但未产出） |
| 有缺失 | 无缺口 | **切句层丢文案**（内容未进入流水线）→ 查 Phase 2.6 |
| 无缺失 | 无缺口 | 文案完整；若音频仍缺内容，转 Phase 3 音频口径 |

**丢失形态判读**（历史真实案例：英语 8.06% / 德语 10.16% / 俄语 7.63%）：

- **零散丢句**：每处仅 2~9 词、全章约 30 处 → 分段合成时个别片段生成失败被静默丢弃
- **时间轴无空洞**：相邻字幕段间隔均 < 3s，缺失处无时间空隙 → 属"生成时被跳过"，非"时间轴压缩"
- 若出现**整段连续丢失**或**时间轴空洞**，属另一类缺陷（截断/超时），需单独定界

#### 无原文留证时的补救：源锚定法

历史批次未存下发原文时，可用「输出句在源文件中的位置」反推应下发文案：

1. 取输出中长度 ≥ 25 字符的句子作为**锚点**（至少 2 句）；
2. 在源 txt 中定位**首锚**与**末锚**，两锚之间即"应下发文案"；
3. 对该片段与输出做词对齐。

> ⚠️ 该方法仅用于**历史数据补救**，且必须遵守下方踩坑项 3。新批次一律走"保存原文"的正路。

#### 强制踩坑项（v1.1.0 实测踩过，必须遵守）

| # | 坑 | 现象 | 正确做法 |
|---|----|------|---------|
| 1 | **`taskStatus=2` ≠ 文案完整** | 任务"成功"但英语丢了 8.06% | 成功只代表有产物；**必须独立跑文案比对**，不得以 status 作为通过依据 |
| 2 | **`startOffset`/`endOffset` 是相对每段的偏移** | 当作全文偏移做覆盖分析，会得出"98% 未覆盖"的完全错误结论 | 严禁用它做全文覆盖分析；只能做段内自校验 `source[a:b] == text` |
| 3 | **锚点命中重复句会伪阳性** | 第 12 章首句与第 11 章末句相同，锚点取到较早那次，把章标题圈进"应下发文案"，误报丢 18 词 | 锚点命中多处时结合章标题边界复核；可疑任务须人工确认后再定论 |
| 4 | **省略号 `...` 被拆成 `.. .`** | 压缩空白后逐字符比对不一致，易误判 | 属服务端拼接写法，**不算丢失**；以"去标点后逐字符一致"为最终判据 |

#### 测试用例

```yaml
  TC-TXT-001: 单任务输入/输出词级一致
    断言: 缺失词 = 0 且 多余词 = 0

  TC-TXT-002: 并发下输入/输出一致（必测 M1，低并发+高并发都要做）
    口径A 低并发(1~2): 串行/低并发下发 N 个任务，逐任务比对（排除排队干扰的干净链路）
    口径B 高并发(打满服务上限，如 5/16): 并发持续下发，逐任务比对
    断言: 两个口径下整体缺失率均 = 0.000%，且无单任务缺失
    ⚠️ 必须两个口径都做 —— 历史文案丢失**只在并发下复现**，串行从未复现；
       只做其中一个不算完成 M1

  TC-TXT-003: 长文案一致性（1500 词 / 整章）
    断言: 长文案不引入额外缺失

  TC-TXT-004: 多语种并发一致性（6 语种整章）
    断言: 各语种缺失率 = 0；若仅个别语种丢 → 定位该语种链路

  TC-TXT-005: paraIndex 连续性校验
    断言: 序号无缺口

  TC-TXT-006: 串任务 / 串词检测
    方法: 丢失任务的返回文本与其他任务输入做词集重合度比较
    断言: 「与自身文案重合度」>「与其它文案重合度」

  TC-TXT-007: 标点写法差异不误判
    断言: 去标点后逐字符 100% 一致

  TC-TXT-008: 服务异常恢复后的首批任务（高发窗口）
    背景: 服务异常恢复后的首跑是文案丢失高发窗口
    断言: 恢复后先探活短文本再批量下发；首批结果必须逐任务比对

  TC-TXT-009: 参数对照排除法
    方法: 同章文案拆开 lang / voice 变量做 2×2 对照
    断言: 明确丢失是否与调用参数相关

  TC-TXT-010: 复现性验证
    方法: 与丢失批次同参数、同并发复跑
    断言: 复跑 0 缺失 → 判定为服务端间歇性异常，非参数问题
```

### Phase 2.6: 切句（分句）质量与完整性测试 ★ 必测（M4，与 M1 联动）

**测试目的**：切句是「文本 → TTS」之间的**第一道关口**，出问题会直接导致两类后果：

| 后果 | 说明 |
|---|---|
| ① **丢文案** | 内容在进入流水线前就没了 → 正是 M1 定界表里「通道A有缺失但 paraIndex 无缺口 = **切句层丢文案**」所指 |
| ② **超长句 / 碎片句** | 直接影响合成成功率、漏词与音频质量（破音、断续） |
| ③ **段落结构丢失（最隐蔽）** | 下发文本被拼成单段落 → `paraIndex` 恒为 0 → 切句退化：**超长段（实测最长 1757 字）/ 不可能语速（最高 277 字/秒）/ 固定时长静默占位（81.64s）**；**文本口径 0 缺失，但音频实际缺失 20~46%**（2026-09-24 实测）。**属 M0 前置失守，不是服务端偶发** |

> ⚠️ **段落结构丢失的定位方法（3 步）**：
> ① 查 `paraIndex`：`distinct(paraIndex) == 1`（恒为 0）→ 段落结构已丢；
> ② 查段长分布：出现 >200 字的段、或 `chars/段时长` > 15 字/秒（时间不够）、或恰好 81.64s 的段 → 切句退化；
> ③ 用 ASR 整段复算：识别字数 ÷ 原文去空白字数，< 90% 即存在音频内容缺失。
> 处置：**按 M0 修正语料（保留换行）后重跑**，不要把它当成服务端缺陷写进报告结论。

```yaml
  # ── 完整性：判「有没有丢」 ──────────────────────────────
  TC-SPL-001: 各切句方案词数一致性
    方法: 同章文本 → 各方案分别切句 → 归一化后比词数
    断言: 各方案词数一致（±1 词以内的分词差异可接受）

  TC-SPL-002: 切句结果与源文对齐  ★ 与 M1 联动
    方法: 各方案输出合并后与源章文本做词对齐
    断言: 缺失词 = 0
    说明: 此项不通过 = M1「通道A有缺失但 paraIndex 无缺口」所指的**切句层丢文案**

  TC-SPL-003: 切句数 vs 下游段数关系  ★ 必测（M4/M5 交界）
    方法: 每章统计三个数并检查**关系是否合理**：
          ① 句数 = distinct paraIndex 数
          ② metadata segments 条数
          ③ SRT / 字幕条目数
    断言: ② >= ①  —— 一句可拆多条字幕，多出属正常，**不是缺陷**
          ③ == ②  —— 派生环节不应丢条目或多条目
          paraIndex 序列无缺口

    用户反馈: 「切句数对不上字幕数」——先按本用例判**是正常拆句还是真丢**，不要直接判缺陷

  # ── 质量：判「切得好不好」 ──────────────────────────────
  TC-SPL-004: 超长句检测  ★ 历史问题
    方法: 统计每句字符数，看最大值与分布
    断言: 单句不超过 TTS 上限（各方案正常范围实测 117~291 字）
    ⚠️ 历史问题: **换行符切句最长 219~477 字，严重超 TTS 上限**
       → 超长句会导致合成失败/截断/漏词，选型时必须排除该方案

  TC-SPL-005: 碎片句检测  ★ 历史问题
    方法: 统计 1~5 字句的数量与占比
    断言: 无异常碎片（合理短句如 "Really?" 可接受）
    ⚠️ 历史问题: **换行符切句存在换行截断产生的 1~5 字碎片**
       → 碎片句会让语音断续、破坏韵律

  TC-SPL-006: 切句粒度合理性
    方法: 看句数 / 均长 / 均句时长
    断言: 均长 37~55 字、均句时长 3.0~4.3s 为合理区间（pysbd/pyset/API 实测均在此区间）
    参考: pyset 切分最细（比 pysbd 多 10~22 句）；pysbd 会合并部分短句（略粗于 API）

  TC-SPL-007: 切句耗时
    参考基线: 换行符 ~0ms ｜ pysbd 0.010~0.061s ｜ pyset 0.010~0.055s ｜ API 0.27~0.99s（有超时风险）

  # ── 结构性缺陷：判「切得对不对」 ★ 用户反馈高发 ────────────
  TC-SPL-008: 句子截断检测  ★ 必测
    方法:
      ① 逐句在源文中做**连续子串定位** —— 定位不到 = 句子被改写或截断
      ② 校验每句**末字符**是否为句末标点（. ! ? … 。！？ " 」 』 等）
      ③ 用「切句输出拼接」与源文做词对齐，看是否丢失尾段
    断言: 每句都能在源文中定位；无缺失尾段；句子不以半个词/半个词尾结尾
    异常表现: 句子中途被切断 → 该句尾部内容丢失（属**切句层丢文案**，与 M1 联动）
    脚本: 用 TC-SPL-002 的同一套词对齐结果即可，无需额外数据

  TC-SPL-009: 句子顺序一致性  ★ 必测
    方法: 对每句在源文中定位**起始位置**，检查该位置序列是否**严格单调递增**
    断言: 顺序与源文完全一致；无乱序、无重复、无回跳
    异常表现: 顺序错乱（后段提前/前段挪后）→ 听众听到语义颠倒，且词对齐会同时出现
              "缺失"与"多余"，容易被误判成"漏文案"
    ⚠️ 判读要点: 若 M1 出现缺失，先跑本用例排除乱序 —— 乱序与真丢失的处置完全不同
       （乱序 = 切句/拼接顺序问题；真丢失 = 生成阶段丢弃）
```

> **TTS 特有强化（重要）**：TTS 是**按注入顺序逐句合成**的，一旦乱序，
> **音频里的朗读顺序就是错的**——内容一个没少，但听众听到的是颠三倒四的故事。
> 因此 **TC-SPL-009 的优先级高于"词数是否一致"**：词数对得上也可能是乱序。

| 优先级 | 方案 | 适用 | 理由 |
|:--:|---|---|---|
| 🥇 首选 | **pysbd** | en/de/ru/es/fr | 质量好、极快、无网络依赖、无版本限制 |
| 🥇 首选 | **pyset** | 全语言（非英语 en 降级） | 切分最细（比 pysbd 多 10~20% 句数）；需 Python 3.14+ |
| 🥈 备选 | API | 全语言 | 质量最好，但依赖网络、有超时风险 |
| ❌ 不推荐 | 换行符 | 仅无工具时兜底 | 质量维度全面落后：超长段（最长 477 字）、碎片、语义混杂 |

```yaml
       IndexTTS-2.5 西语"发现存在杂音/齿音"，高频占比 15~17%（英语约 2%），
       响度 -13.5dBFS 比英语高约 6dB；同一批次 Higgs/pysbd 方案"未发现杂音/嘶嘶声"
    → 结论：**杂音问题与模型/语种强相关，必须逐模型 + 逐语种判定**（该结论与接口无关，仍有效）

  TC-AUD-010: 破音 / 爆音人工听测  ★ 必测（M2）
    方法: 对每条抽查音频**人工听测**，逐条记录"有无破音/爆音/卡顿"
    预期: 无破音、无爆音
    要求: 结论必须写明"听测人 / 抽样文件 / 抽样方式"，不得只写"未发现"
    ⚠️ 客观指标不能替代人工听测（历史：同一批英语音频，波形报告称"无爆音"、
       另一份结论表称"存在爆音"，两份结论相反 → 以人工听测为准）

  TC-AUD-011: 抽样覆盖要求
    方法: 每次至少覆盖【大章(≥8000字符) + 中章 + 小章】各 1 条，且**每个被测语种都要抽**
    预期: 不得只抽一个语种或只抽短文本就下"音质通过"的结论
```

**音质结论的写法要求（避免历史报告中出现过的自相矛盾）：**

| 要求 | 说明 |
|---|---|
| 客观数据与主观结论**分别列示** | 先列峰值/RMS/高频占比等实测值，再列人工听测结论，不得只给一个"通过/不通过" |
| 冲突时要显式说明 | 若客观指标与人工听测不一致，必须写明冲突并说明采信哪一个及理由 |

| 附抽样清单 | 列出实际听测了哪些文件、哪几个时间段 |

### Phase 5.5: 字幕完整性（丢字幕 M5）与时间轴校验

> 本阶段只解 metadata + 派生 SRT，**不依赖音频/ASR**，成本极低，**建议与 Phase 2.5 同批执行**。
> ⚠️ **M5 丢字幕是每次必测项**——性能测试、稳定性测试、平常测试都要查，不得省略。

**先理清三个数（这是判丢字幕的前提，也是最容易判错的地方）：**

```
read_content ──切句──> 句子[]                句数 = distinct paraIndex 数
                        └─合成─> metadata segments[]   ② segments 条数  ≥  ① 句数（一句可拆多条字幕）
                                   └─派生─> SRT 文件     ③ SRT 条目数  应 == ②
```

| 关系 | 正确判据 | 说明 |
|---|---|---|
| ① vs ② | **② ≥ ①** | 一句可拆多条字幕，② 大于 ① **属正常，不是缺陷** |
| ② vs ③ | **③ = ②** | 派生环节不应丢条目/多条目 |
| ① 自身 | **paraIndex 无缺口** | 缺口 = 丢句（与 Phase 2.5 通道 B 一致） |
| ❌ 错误判据 | ~~①=②=③~~ | 实测同一句会拆多条，此判据必然误报 |

```yaml
  TC-SUB-007: 字幕条数关系校验  ★ M5 核心
    方法: 统计 ① distinct paraIndex 数、② metadata segments 条数、③ SRT 条目数
    断言: ② >= ①；③ == ②；paraIndex 无缺口
    ⚠️ 不要断言三数相等（实测 paraIndex=230 一句拆 2 条字幕）
    判缺陷: paraIndex 有缺口 → 丢句｜③ != ② → 派生丢条目｜② < ① → 必为错误
    脚本: locate_chapter_loss.py（输出缺口+空洞）

  TC-SUB-008: 空字幕段检测  ★ M5
    方法: 统计 (text or "").strip() == "" 的 segment 数
    断言: 0 条
    说明: 空字幕段 = 该条字幕无内容，观众看到空白字幕；实测正常批次为 0

  TC-SUB-009: 字幕内容可定位性  ★ M5
    方法: 每条字幕 text 在源文中做连续子串定位
    断言: 全部可定位（定位不到 = 内容被改写/截断，属丢字幕内容）

  TC-SUB-010: 字幕时间轴覆盖率  ★ M5
    方法: ① 相邻段间隔 > 3s 计为空洞（TC-SUB-005）；② 字幕总时长 / 音频时长
    断言: 空洞 = 0；字幕覆盖音频全程（音频有声音的时间段必须有字幕）
    说明: 时间轴空洞 = 音频在讲但没字幕 → 最典型的"丢字幕"表现

  TC-SUB-001: 时间戳单调性
    方法: 逐段校验 startMs < endMs，且 endMs[i] <= startMs[i+1]（允许微小间隙）
    预期: 100% 通过；无重叠、无倒序

  TC-SUB-002: offset 段内自校验  ★ 注意语义
    方法: 对每段校验 source[startOffset:endOffset] == text
    预期: 100% 匹配
    ⚠️ startOffset/endOffset 是**段内偏移**（相对该段），
       **不是**相对整篇 read_content 的全局偏移（见 Phase 2.5 踩坑项 2）。
       严禁用它们做全文覆盖分析，只能做本用例的段内自校验。

  TC-SUB-003: paraIndex 连续性与覆盖
    方法: 取所有 paraIndex >= 0 的段，检查序号是否连续无缺口
    预期: 无缺口（缺口 = 丢失句，与 Phase 2.5 通道 B 一致）

  TC-SUB-004: 段落索引正确性
    方法: 下发多段落文本，检查 paraIndex 分布与段落边界；同段 text 拼接后应与原文段落一致
    预期: 无跨段落混叠

  TC-SUB-005: 时间轴空洞检测
    方法: 相邻字幕段间隔 > 3s 计为空洞
    预期: 0 个
    脚本: locate_chapter_loss.py（同时输出缺失块与空洞）
    ⚠️ 判读: 有空洞 = 截断/超时类缺陷；**无空洞但内容缺失 = 生成时静默跳过**（两类缺陷定性完全不同）

  TC-SUB-006: 跨引擎/跨模型字幕一致性
    方法: 同文本分别用不同模型合成，比对 metadata 结构
    预期: 结构一致；text 内容与原文一致（时间戳因语速不同而有差异属正常）
```

### Phase 8: 语义与停顿专项

> 前序 Phase 判的是"内容有没有丢"，本阶段判"念得对不对"。需要音频 + ASR（large-v3）。

```yaml
  TC-VT-001: 逐句文案比对
    方法: Whisper 转写获取句级时间戳，逐句与原文比对，标记缺失/多出/替换
    预期: 句级准确率 ≥ 95%

  TC-VT-002: 语义实体保留率  ★ 漏词高发区
    方法: 从原文提取实体（数字 / 日期 / 金额 / 人名 / 地名），检查转录中是否保留
    预期: 实体保留率 ≥ 98%
    ⚠️ 历史案例: 原文 "that servant needs surgery. I'll give you 3 million"
       输出从 "that servant" 直接接到 "I'll give you three million"，**漏掉 needs surgery**
       → 漏词集中在短块与数字附近，须专项抽查

  TC-VT-003: 数字/日期读法正确性
    方法: 下发含数字、日期、金额的文本，人工+ASR 核对读法
    预期: 正确率 ≥ 95%
    ⚠️ 注意区分「读错」与「文本写法差异」（如 "three" vs "3"、"23" vs "2 3"）

  TC-VT-004: 标点停顿
    方法: 分析 metadata 段间隔；句号后停顿 > 300ms，段落间 > 800ms
    预期: 标点停顿正确率 ≥ 90%，段落停顿正确率 ≥ 95%

  TC-VT-005: 多音字 / 专有名词发音
    方法: 人工听测（中文多音字、人名地名）
    预期: 正确率 ≥ 90%
```

**ASR 模型选择（直接影响本阶段结论可信度）**

| 模型 | 用途 | 注意 |
|------|------|------|
| `faster-whisper-large-v3` | **正式验收** | 首选；体积约 2.9GB |
| `faster-whisper-base` | 快速自查 / 抽检 | **识别能力弱，不得用于验收判定** |

> ⚠️ 语种差异极大：base 模型对**西语/俄语**的识别误差远高于英语，会把 ASR 误差误判成 TTS 漏词
> （历史案例：西语 base 测出 30.81% WER，换 large-v3 复核后大幅下降）。
> **结论：非英语语种的 WER/漏词判定必须用 large-v3，或标注"仅供参考"。**

### Phase 9: 产物与分发测试（MP3 文件 / COS 链接 / 任务生命周期）

> **为什么单独成阶段**：本接口的交付物不是一句"合成成功"，而是
> **MP3 文件 + metadata/SRT + 时效签名链接**。文案对、音频对，业务仍可能**拿不到、播不好、打不开**。
> 0924 批次就暴露了两类只属于这一层的问题：**产物可见性竞态**（18/225 立即下载返回 `NoSuchKey`）与
> **任务长时间卡死**（`status=67` 持续 1940s）。

**产物链路**

```
read_content ──切句/分段──> 分段合成 ──编码──> MP3（落 COS）──> audio_url（时效签名）
                                        └──> metadata.json / SRT ──> metadata_url（时效签名）
```

**实测基线（0924 日语批次，可作为断言对照）**

| 项 | 实测值 |
|---|---|
| 采样率 / 声道 / 码率 | **24000 Hz / mono / ≈51 kbps（VBR 48.9~52.3k）** |
| 体积（5000 字任务） | 3.92~4.70 MB（中位 4.50 MB），≈12 分钟音频 |
| 标签 | 容器仅 `encoder=Lavf60.16.100`；**无 title/artist** |
| 时长一致性 | 音频 vs metadata 末段 `endMs` 差 ≤63 ms |
| 链接 | `audio_url` → COS **香港** `audiobook/<taskId>.mp3`；`metadata_url` → COS **广州**（q-sign） |
| 命名 | **`<taskId>.mp3`**（可预测、可枚举） |

### 4. 切句问题（M4）

数据来源：`测试报告\切句接口对比测试_0730`、`pysbd切句多语种测试报告_0731.md`（前 5 行）+ 用户反馈（后 3 行）

| 缺陷 | 来源 | 方案 / 场景 | 实测表现 | 判异常依据 |
|---|---|---|---|---|
| **超长句** | 报告 | 换行符切句 | 最长 **219~477 字**，严重超 TTS 上限（其它方案 117~291 字） | 单句 >291 字 |
| **碎片句** | 报告 | 换行符切句 | 换行截断产生 **1~5 字碎片** | 出现非合理短句 |
| **语义混杂** | 报告 | 换行符切句 | 一段含多句；均长 92~111 字（其它方案 37~55 字） | 均长明显偏大 |
| **语言降级** | 报告 | pysbd / pyset / API | 葡语及其它非英语语种**降级 `en` 模型**，多语种结论不可直接采信 | 报告未标注降级 |
| **网络依赖风险** | 报告 | API 切句 | 0.27~0.99s，本地方案仅 0.01~0.06s | 超时即失败 |
| **句子被截断** | **用户反馈** | 待复现定位 | 切句后句子中途被切断，尾部内容丢失 | 句子不能完整定位到源文 / 末字符非句末标点 |
| **文案顺序错乱** | **用户反馈** | 待复现定位 | 切句后句子顺序与源文不一致 | 句子源文位置序列非严格递增 |
| **切句数对不上字幕数** | **用户反馈** | 待复现定位 | 切句数与 segments 数 / 字幕条目数不一致 | 三者不相等 |
| **段落结构丢失 → 超长段 + 音频内容缺失** | **0924 实测**（日/韩 10 并发 × 30 分钟） | **单段落语料下发**（换行被抹平） | `paraIndex` 恒为 0；超长段最长 **1757 字**（正常中位 42 字）；语速达 **277 字/秒**（正常 5~9）；出现 **81.64s** 固定时长静默占位；**音频实际缺失 20~46%**（整段 ASR 实测韩语 0040 缺 34.55%、0071 缺 45.97%，超长段丢失 76~90%） | 段落数 ≥2 且 `distinct(paraIndex) > 1`；无 >200 字的段；ASR 识别字数 ≥ 原文 90% |

> ⚠️ **最后一项（段落结构丢失）是 2026-09-24 新沉淀的失效模式，属"测试侧语料问题"而非服务端缺陷**：
> 它会让 **M1 文本口径显示 0 缺失**（因为 metadata 文本是切句结果原样拼接），却让音频真实缺内容，
> 极易误判成服务端 bug。**已在顶部新增 M0 前置门禁**：语料必须保留换行，单发探针 `paraIndex` 非恒定 0 才允许批量下发。

> **后 3 项为用户反馈的高发问题，但尚无实验数据。** 每次执行 M4 时**必须专门查这 3 项**
> （对应 TC-SPL-003 / 008 / 009）；一旦复现，**立即留存**：源文、各方案切句输出、
> 返回 metadata、SRT、音频，并回填本表补充实测数据。

> **换行符切句不应作为生产方案**（超长句 + 碎片 + 语义混杂三项全不达标），
> 仅可作无任何工具时的兜底。首选 pysbd（en/de/ru/es/fr）或 pyset（需 Python 3.14+）。

| **文案缺失率** | 缺失词 / 输入词 | **0.000%** |
| 文案缺失词数 | `delete` + `replace` 左侧词数 | **0** |
| 文案多余词数 | `insert` + `replace` 右侧词数 | **0** |
| 缺失块数 | 连续缺失片段数 | 0 |
| paraIndex 缺口数 | 序号缺口个数 | **0** |
| 相似度 | `SequenceMatcher.ratio()` | **1.0000** |
| 去标点后逐字符一致任务占比 | 一致任务 / 总任务 | **100%** |

### 音频/质量指标（Phase 3 / 5 / 6，ASR 与波形口径 —— 不可用于判定漏文案）

| 指标 | 公式 | 目标 |
|------|------|------|
| WER (词错误率) | (S+D+I) / N | < 5% (英文) |
| CER (字错误率) | (S+D+I) / N | < 10% (中文) |
| 漏词率（ASR 口径） | D / N | < 2% |
| 多词率（ASR 口径） | I / N | < 2% |
| 准确率 | 1 - WER | ≥ 95% |
| MOS | 人工评分 1-5 | ≥ 3.5 |
| 音频截断率 | 音频时长 vs metadata 总时长 | 0%（差值 <1s） |
| 峰值 / 削波 | 波形峰值 | ≤ 0.999（不得触顶 1.000） |
| 任务成功率 | 成功数 / 总数 | ≥ 99% |

> ⚠️ **任务成功率只是"有产物"的比例，与文案完整性无关。** 历史案例：6/6 任务 status=2 成功，其中英语实际丢了 8.06%。两个指标必须分别报告，不得互相替代。

## 关键实践教训（v1.1.0 新增）

| # | 教训 | 依据 |
|---|------|------|
| 1 | **"任务成功"不等于"文案完整"** | 0910 六语种批次 6/6 status=2，实际英/德/俄各丢 8~10% |
| 2 | **判定漏文案只能用文本口径** | ASR 口径含识别误差；西语 base 模型测出 30.81% WER，人工复核后基本非 TTS 漏词 |
| 3 | **文案丢失是间歇性的，不是必然的** | 同一批次同参数复跑 0 缺失；其余 12 个批次全部 0 缺失；仅服务异常恢复后首跑那批真实丢失 |
| 4 | **丢失特征是"零散丢句 + 时间轴无空洞"** | 每处 2~9 词、全章约 30 处，相邻字幕段间隔 <3s |
| 5 | **两个独立通道能互证才可信** | paraIndex 缺口数(30/36/28) 与词对齐缺失块数(31/35/29) 相互印证 |
| 6 | **服务端应增加"请求分段数 vs 返回分段数"一致性校验** | 当前个别片段失败后被静默丢弃，调用方只能靠事后比对发现 |
| 7 | **核对历史数据前先确认源文件** | 0730/0731 的英语源是 `EN-英语.txt`(UTF-16)，不是 `XR3 - EN.txt`；用错源会得出"丢 400 词"的完全错误结论 |
| 8 | **审计脚本自身要先自证** | 本轮排查中出现过 2 次方法性伪阳性（offset 语义误判、重复句锚点误判），修正后才与既有报告吻合 |

| 10 | **必测项不因测试类型而豁免** | 性能/稳定性跑批**同时**产出文案一致性与音质留证；不得用"本次只测性能"跳过 M1~M3 |
