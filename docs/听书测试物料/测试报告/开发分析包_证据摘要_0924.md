## 结论

1. **跨小时重新查询仍全部为 `67`（处理中）** → 不是「排队慢」，而是**状态未收敛的孤儿任务**（最久的一个来自 0924 批，已挂约 9 小时）。
2. **`data` 为空、`errorCode=0`、`comment=null`** → 既没有产物，也**没有任何失败原因**，调用方与测试都无法排障，也没有重试入口。
3. **产物对象 404** → 音频确实没有产出（不是产物竞态那种「已生成但暂时不可读」）。
4. 客户端侧唯一的兜底是自身轮询超时（本次 2400s / 跑批 drain 1500s）→ 若调用方按契约一直等，会永久挂住。

## 给开发的建议

- 处理中状态加**超时收敛**：超过阈值（建议按最长任务时长 ×2）自动置 `3(失败)` 并写可读原因；
- 失败/超时必须写 `errorCode` / `comment`（当前 `errorCode=0` 等于不可诊断）；
- 暴露队列与槽位可观测指标（排队数 / 在处理数 / 最长处理时长 / 处理中任务年龄分布）；
- 若属「worker 异常退出未回写状态」，建议增加任务状态的对账（reconcile）与自动补偿。
